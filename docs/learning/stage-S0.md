# S0 学习记录：故障模型与真值集

## 故障故事

订单 API 的 5xx 告警出现后，调查者需要区分三种原因：数据库连接池耗尽、部署引入错误配置、下游调用超时。告警本身只说明症状，不能直接证明根因。两个案例故意保留证据缺口或冲突，正确结果应是“无法判定”。

## 四类信号各说明什么

- **日志**给出服务在某时刻观察到的错误和上下文。单条日志可能误导，例如下游故障案例里有数据库池警告。
- **指标**显示一段时间内的数量、比例或延迟变化。它适合找异常范围，但相关变化本身不证明因果。
- **追踪**把一次请求拆成有 trace ID 的 span，可定位耗时或失败发生在哪个服务边界。
- **部署事件**记录版本和变更时间。变更先于故障是线索，仍需日志、指标或追踪支持因果关系。

S0 将四类内容作为带原始属性的合成记录保存。后续假设账本应引用记录 ID，不能只引用模型生成的摘要。

## 关键文件与数据结构

- `scripts/generate_dataset.py`：固定 `random.Random(20261019)`，生成 8 个 incident，并在写盘前检查案例数量、标签数量和信号来源。
- `data/incidents.jsonl`：每行包含 incident 时间窗、告警、时间线和四类观测记录。每条记录有 ID、UTC 时间、服务和属性。
- `data/labels.json`：独立保存类别、根因和是否可判定。调查输入不应读取此文件。
- `docs/incident-contract.md`：因果模型、易混淆解释、数据契约和评测指标口径。

## 如何证实或证伪假设

`pool-01` 的 `pool-01-m1` 显示 40/40 连接在用，`pool-01-m2` 显示等待 2130 ms，`pool-01-l1` 记录获取连接超时；数据库健康记录仍为 healthy。三项线索支持连接池耗尽，也降低“数据库整体不可用”的可能性。

`config-01` 的 `config-01-d1` 记录 `order-v15` 在 09:02 UTC 部署；`config-01-l1` 与 `config-01-t1` 在 09:05 UTC 记录配置校验失败，错误率指标也标记同一版本。变更时间、版本和失败信号相符，支持部署配置错误。

`downstream-01` 的数据库警告容易带偏调查。`downstream-01-m3` 显示连接池仅 9/40，`downstream-01-t1` 显示慢 span 位于 `order.downstream.call`，`downstream-01-l1` 的 trace ID 与追踪一致。证据更支持下游超时；数据库警告不足以证明连接池耗尽。

## 两条异常链

1. **连接池链**：连接等待升高 → `order` 获取连接超时 → 请求失败 → gateway 5xx 升高。数据库仍健康，因此需区分“连接池耗尽”和“数据库不可用”。
2. **配置变更链**：`order-v15` 部署 → 新版本配置校验失败 → 依赖调用前失败 → 5xx 升高。若部署记录与失败版本对不上，应撤回或降低该假设。

## 亲手实验：证据删减（约 10–20 分钟）

1. 暂时不要打开 `data/labels.json`。在 `data/incidents.jsonl` 找到 `config-01`，写下最可能根因，并记下支持它的部署、日志和指标 `record_id`。
2. 复制该行到临时文本，只删去 `deployments` 数组中的记录。重新判断：配置错误仍可疑，但“部署导致”这条因果链缺少部署证据，应降低置信度或标为未证实。
3. 找到 `downstream-01`，对比数据库池指标、日志和 span。解释为什么数据库警告不能压过池使用率与慢 span 的证据。
4. 恢复原数据：运行生成命令。确认数据哈希回到上面的值，再打开标签文件核对。

## 面试追问

**问：为什么标签和 incident 数据分开？**

答：避免调查输入直接泄漏答案；评测器可以读标签，调查器只读观测数据。

**问：为什么证据不足要作为独立标签？**

答：真实调查会遇到数据源缺失或信号冲突。强迫每例选根因会奖励猜测，也掩盖系统边界。

**问：同一时间出现部署和故障，是否足以归因部署？**

答：不足。还要核对受影响版本、错误内容和请求追踪；时间相关只是候选证据，不自动构成因果。

## 未覆盖边界

样本只有 8 例，不能代表生产分布，也不能据此宣称模型准确率。数据是合成静态观测，尚无服务、流量、真实故障注入、查询工具或模型调查。S1 开始前，人工需再检查数据语义和标签是否适合后续工具读取。
